## F03-02: what the change does
- New `security/dep_delta.ts`: `manifestDelta(path, base, next)` returns the (ecosystem, name, spec, version?) pairs a change added or changed, from `package.json` (dependencies, devDependencies, optionalDependencies), `package-lock.json` (exact versions, scoped and nested names) and `requirements.txt`. A range or a git/URL/path/workspace source has no `version`. An unreadable file returns `unreadable`, never an empty clean list. No network, no process call.
- `gates/security_gate.ts`: `runSecurityGate(files, override?, { advisoryLookup? })`. Per manifest it adds non-blocking Medium findings:
  - `Dependency Check`: "adds or changes N dependencies that were not checked for known vulnerabilities: ...", with the reason (no advisory source configured, or the lookup did not answer) and a note that ranges cannot be checked from a manifest.
  - `Known Vulnerability`: only when a synchronous advisory source answered with ids for an exact pair.
  - A source that returns `undefined` or throws is "not checked", never clean. An unreadable `package.json` keeps its existing "Scan Limit" finding (not duplicated).
  - Never forgiven as pre-existing, never blocks.
- `verify/surface_text.ts`: the notes line for these two categories says "not checked ... not a clean result" (before it printed "Dependency Check in package.json:1").
- Tests: `gates/security_gate_f0302.test.ts` (18, all failed before: module missing), 3 added to `verify/surface_text.test.ts`.

## E3c: what the change does
- `recovery/heal.ts`: `HealResult.triedStates` = the starting failing state plus every candidate the loop verified and saw fail. Not set when a round's check could not run (infrastructure stop says nothing about the code).
- `recovery/resolve_verification.ts`: passes `healed.triedStates` to escalation.
- `recovery/escalate.ts`: `runEscalation(..., deps, { alreadyTried })` seeds its oscillation guard with them. A candidate equal to a state repair already failed ends escalation before verification (the guard's existing message).
- `lifecycle.ts` and `server.ts` needed no change: both reach repair-then-escalate through `resolveVerification`. Their direct escalation after a compile failure has no repair loop.
- Tests: 2 in `heal.test.ts`, 3 in `escalate_infrastructure.test.ts`, 1 in `resolve_verification.test.ts`. The "equal state is refused" and "starting state and every candidate returned" and "passed to escalation" tests failed before.
- Behaviour to know: a hit ends escalation at once instead of using its second attempt.
