# ISO/IEC 42001 — Data and Dependency Governance

## 1. Data Handling & Secrets Protection
- A scan for secrets and high-entropy strings (`secrets.ts`) runs on every proposed change inside `verifyInSandbox`, before any copy of the project is made. It recognises only some secret formats. An early internal probe found 9 of 22 synthetic tokens; the scanner has been widened since, and that probe's token set was not kept, so the figure cannot be repeated and is not a current measurement. The formats it blocks, and the ones it only removes from prompts, are listed in the test files `secrets_formats.test.ts` and `secrets_vendor_formats.test.ts`. A figure measured on a set rebuilt for this repository is on `docs/WHAT_PURIX_CHECKS.md` (finding F03-07); it is not comparable with the 9 of 22. Since 2026-11-08 (session C1) the write scan also blocks an unquoted password or token, a hex key under a key name, a database URL with a password, a short quoted password, and a secret written as several adjacent string pieces, when the value is not a placeholder. On a set of 17 probes written by that session it blocked 17 where it had blocked 4, and it flagged 1 of 30 ordinary lines (a placeholder under the older key-assignment rule). A secret split across variables, encoded (for example base64) or unlike any listed shape still passes; those figures come from a set written by the session that made the change and no one else has repeated them. The change was ratified on 2026-11-11 after the scan was run over the Purix repository (858 files): outside tests and fixtures it found two false blocks (model ids flagged by the older entropy rule), which were fixed, and none remained. That is one repository, gitleaks was not run, and a reviewer can move a shape back to scrub-only by one list entry (`docs/DECISIONS-2026-11-11.md`).
- `secrets_manager.ts` stores credentials set with `secret-set` and `secret-rotate`.
- What goes to the model provider you choose is the text of the files Purix is working on. Text that matches a known secret format is replaced with `[REDACTED:<kind>]` in every prompt before it is sent and in every reply before it is used (`security/outbound_scrub.ts`, called from `llm/classify.ts`), including the files of the component being changed. A secret in a format the list does not know, or one that is split or encoded, is sent as it is.
- A cost ceiling (`budget_state`) limits model spend.

## 2. Dependency & Supply Chain Controls
- `purix audit` (not the verification step) runs the version-pinning check (`checkVersionPinning`) and the vulnerability scan (`runVulnScan`: pnpm, yarn or npm audit for TypeScript projects, `pip-audit` for Python). During verification, a change that adds a dependency is looked up for known vulnerabilities and for whether the package exists only when `PURIX_DEP_LOOKUP` is set (see the next bullets); it is off by default, so by default those dependencies are listed as "not checked". Until 2026-11-07 the TypeScript scan returned nothing for pnpm 10 and 11 projects that had known advisories and for a Yarn 4 project, and read a registry error as a clean scan. It now reads pnpm 10 and 11, Yarn 1 and 4, and npm 10 reports and reports "skipped" for any output that is not an audit report. That was checked on Linux against recorded real output of those versions; Yarn 2 and 3, Windows and macOS were not run, and no one but the session that wrote the fix has re-run it.
- The security gate (`security_gate.ts`) compares dependency names in a `package.json` against a list of 30 popular names to flag typosquats: one edit, or two for a name of 8 letters or more, and two neighbouring letters swapped count as one. About 120 real package names are never flagged (`POPULAR_REAL`). This rule reads `dependencies` and `devDependencies` only. A look-alike of a package that is on neither list is not flagged, and nothing is looked up.
- Since 2026-11-12 the gate also judges what a change did to a dependency manifest, against the file's previous content (`gates/manifest_delta.ts`, `security/dep_delta.ts`). A git, GitHub-shorthand, URL or tarball dependency in a `package.json`, an added or changed `preinstall`, `install` or `postinstall` script, and a changed `registry=` line in `.npmrc` block the change; a path or link dependency and an added version override are noted. It also judges a lockfile against its previous content (`gates/lock_delta.ts`, `security/lock_parsers.ts`; `package-lock.json`, `npm-shrinkwrap.json`, `pnpm-lock.yaml`, `yarn.lock`, `poetry.lock`, `uv.lock`): an entry added or changed to a non-registry source, to a download host no earlier entry used, or with a different integrity value for the same name and version blocks the change, and a file the reader cannot parse is reported as unreadable, never as clean. The dependencies a change adds or raises (`package.json`, `package-lock.json`, `requirements.txt`, `pyproject.toml`) are listed as "not checked" for known vulnerabilities unless the lookup is switched on. The `pnpm-lock.yaml` and `yarn.lock` readers were written from format knowledge and hand-made fixtures, not run on real files from each tool. The sessions that wrote this also wrote its tests, and no one else has read it.
- The lookup is opt-in and off by default (`PURIX_DEP_LOOKUP=osv|registry|all`; decision D-q in `docs/DECISIONS-2026-11-12.md`). When on, only package names and exact versions leave the machine, to the package registry and to `api.osv.dev`; a name that resolves to a private registry is never sent to OSV. An ordinary advisory is reported (Medium) and does not block; an OSV malicious-package record (`MAL-` id) blocks (decision D-r); a name the registry does not have, or first published under 7 days ago, is reported (Medium) and does not block. Anything that fails (offline, a refused request, an unexpected reply) is "not checked", never clean. It has never run against the live services: this was built and tested without network access.
- Tools Purix installs for you (type checker, test runner, linter) come from one catalog with exact versions and file hashes (`packages/core/src/tools/catalog_data.ts`). Each install needs your confirmation, npm installs run with `--ignore-scripts`, and each request and install is recorded in the hash-chained log.
