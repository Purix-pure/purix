# EU AI Act — Annex IV Technical Documentation

## 1. System Description & Intended Purpose
Purix is a verification and governance layer (`@purix/core`, `@purix/cli`, `@purix/mcp-server`) for AI-generated code edits. It applies deterministic override floors, verifies changes for TypeScript and Python projects in a sandbox, and writes a hash-chained log of landed changes, tool installs and drift. The hosted API is in a separate repository and is not described here.

## 2. Risk Controls & Thresholds
- **TrustGate (`packages/core/src/gates/trustgate.ts`):** reject below `0.35`; auto-commit at `0.75` or above only if the change is not contract-changing, the touched files have related tests, no test assertion was weakened, the classifier raised no injection flag, and verification ran isolated. Anything else goes to a human or is aborted. The confidence is the model's own stated figure. No safety rate is stated for the `0.75` cutoff, because nothing in this repository measures how often a change above it is wrong.
- **Deterministic Override Floors (DOF):** default patterns cover auth, identity and security folders, migrations, `.env` files, `CODEOWNERS`, CI workflows, Dockerfiles, package manifests and lockfiles, and agent settings folders (`DEFAULT_DOF_PATTERNS` in `gates/trustgate.ts`). A `dof-patterns.json` in the project root adds to these defaults and never replaces them; `dof-patterns.json`, `purix.config.json` and the policy file are always held. A change touching a matching file always goes to human confirmation (`server.ts`, `lifecycle.ts`). A file that is not registered to a component is not covered (`docs/EVIDENCE.md`). The floor applies to edits that go through Purix, not to direct writes.
- **Security Gate (`packages/core/src/gates/security_gate.ts`):** runs inside `verifyInSandbox` on every write path. It checks for hardcoded secrets, a few SQL-injection, command-injection and weak-cryptography patterns, three shell-script patterns, typosquatted dependency names in `package.json`, and what a change did to a dependency manifest (a git or tarball source, an install script or a changed registry blocks; see `iso-42001/data-and-dependency-governance.md`). Findings the file already had before the change are shown as advisories and do not block; only findings the change adds block, and secrets are never forgiven as old. Python files are read with the Python rules, and documentation and data files (json, yaml, toml, ini, csv, lock) are listed as not read by the code rules. Go, Rust, Ruby, PHP, HTML and Makefile files have no rules of their own and are read with the JavaScript rules, each listed as such, so a clean result there is weaker. An internal probe found it blocked 5 of 42 dangerous examples; that probe was run before these changes and was not re-run for this document, so treat it as a tripwire, not a vulnerability scanner.

## 3. Known Limitations & Remediation History
- **Python parity:** earlier versions hardcoded TypeScript-only verification in `verifyInSandbox`. Verification now dispatches through `getLanguageProvider()` / `resolveLanguage()`. `python_test_integrity.ts` flags weakened or removed assertions in touched Python tests, and a missing tool is reported as `not_installed`, not as a pass.
- **Other languages:** files in languages without a provider are not checked, and the result does not yet say so in every case (see `BETA_SCOPE.md`).
- **Repair and tests:** when a repair runs, it refuses edits to test files and to test-runner configuration (Vitest, Jest, Mocha, Playwright, Cypress, pytest.ini, tox.ini, .coveragerc and snapshot folders) for TypeScript, JavaScript and Python. It does not yet check files that mix test settings with other settings (`package.json`, `pyproject.toml`, `setup.cfg`), and it has no test-file rule for any other language. Those are open defects.

## 4. Language Pack On-Demand Install Model (Phase 3.5)
Language tooling (`pyright`, `pytest`, `ruff`, `pip-audit`) is installed on demand per project through the tools broker (`purix tools install <id>`, ADR-060). Every install shows what will run and needs a human to confirm. Exact versions and file hashes are pinned in the catalog shipped with each release, npm installs skip install scripts, and each request, approval and install is recorded in the hash-chained log.
