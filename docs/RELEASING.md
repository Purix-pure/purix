# Releasing Purix (Release 1, 0.4.0-beta.0)

Steps only the maintainer can do. Nothing here is automated, and nothing in this repository publishes by itself until trusted publishing is turned on (step 3) and a tag is pushed.

0. **Before you publish, close the open items in `docs/RELEASE_READINESS_0.4.0-beta.0.md`** (the legal name in `NOTICE`, CODEOWNERS, and the others listed there as blockers).
1. **Check the registry first.** `npm view @purix/cli versions dist-tags`, and the same for `@purix/core` and `@purix/mcp-server`. On 2026-11-11 all three already existed: `0.1.0`, `0.2.0-beta.0` and `0.3.0-beta.0` are published, `latest` points at `0.3.0-beta.0`, and there is no `beta` tag. So this is not a first publish, and trusted publishing (step 3) can be turned on now. Check again before you publish.
2. **Run the gate.** `node scripts/release-check.mjs full --tag v0.4.0-beta.0`. Every step must be PASS; a step that says NOT CHECKED is not a pass.
3. **Turn on trusted publishing** for each package (package Settings, Publishing access), pointing at this repository and `.github/workflows/publish.yml`. Then push the tag: `git tag v0.4.0-beta.0 && git push origin v0.4.0-beta.0`. The workflow runs the gates, packs the three tarballs once, checks their checksums, and publishes them in order (`@purix/core`, `@purix/mcp-server`, `@purix/cli`) with `--provenance` and the dist-tag `beta` (it derives the tag from the version).
   *Fallback, if trusted publishing cannot be turned on:* publish by hand, one package at a time and in that order, with `pnpm --filter @purix/core publish --access public --tag beta` (and the same for the other two). A manual publish carries no provenance, and you must not then push the `v0.4.0-beta.0` tag, because npm refuses to publish a version twice and the workflow would fail at the publish step.
   npm limits unpublishing. If a version is wrong, `npm deprecate` it and publish a fixed one.
4. **Decide what `latest` means.** Publishing with `--tag beta` leaves `latest` on `0.3.0-beta.0`, so `npm install -g @purix/cli` with no tag keeps installing that older beta, which lacks every change in `0.4.0-beta.0`. There is no stable release, so either move it on purpose (`npm dist-tag add @purix/cli@0.4.0-beta.0 latest`, and the same for the other two) or leave it and accept that. Consider `npm deprecate`-ing `0.1.0` and `0.2.0-beta.0` with a message pointing at the beta.
5. **Clean-machine check.** On Linux, macOS and Windows PowerShell with Node 22.13 or later: `npx @purix/cli@beta --help`, then `npm install -g @purix/cli@beta && purix --help`.
6. **MCP registry.** Publish the **root** `server.json`, which lists `@purix/cli` and starts it as `npx @purix/cli mcp-serve`, the same command the README and `purix connect` use. `@purix/mcp-server` has no executable (`bin`), so the listing in `packages/mcp-server/server.json` could not be started by a registry client; do not publish it (the file can be deleted). `@purix/cli`'s `package.json` carries the matching `mcpName`. The `io.github.purix-pure/` prefix assumes the GitHub account that owns the repository is `purix-pure`; change `server.json` and the `mcpName` fields together if it is not. Then, from the repository root: `mcp-publisher login github`, `mcp-publisher publish`, and confirm with the registry's search endpoint. The npm package must already exist (step 3).
7. **Regenerate the checks page.** `node scripts/generate-checks-page.mjs` after any change to `docs/claims.json` or `docs/client-runs.json`; `pnpm run checks-page:check` fails when the committed page is stale.
8. **Before announcing:** the real-machine report (`docs/client-runs.json`) is filled in for Claude Code first, then Codex, Linux, macOS, Windows PowerShell. Until then the wording stays "reported", not "settled" (see BETA_SCOPE.md).

Support path for Release 1: bugs through GitHub Issues, questions through GitHub Discussions, security reports through the private reporting link in SECURITY.md.
