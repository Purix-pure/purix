**Merge choices, each with its reason.**
1. **Base:** the patch (it applies cleanly to `packages.zip`), then the other uploads laid over it.
2. **E3c:** the two copies were nearly line for line the same. I kept the second session's `heal.ts`, `escalate.ts`, `resolve_verification.ts` and its three test files, and kept the patch session's `oscillation_guard.test.ts` too. They differ in one place: the patch recorded a candidate as "tried" before its check ran, so a check that could not run (a missing tool, a timeout) would have made escalation refuse a candidate that was never tested. The second copy records a state only after it was verified and failed. I also made the loop hand its states back when it stops on a repeated state: the patch session's copy did that and the second copy had left it out, so escalation would not have been told about earlier failed rounds. One new test covers it. All tests of both sessions pass against the kept code.
3. **F03-02:** both real versions kept, with the overlap removed. The blocking rules come from the patch session (non-registry source, install script, `.npmrc` registry). The "not checked" advisory, the lockfile and `requirements.txt` reading and the advisory-source hook come from the other. The patch session's own "Dependency Added" advisory for ordinary dependencies was dropped (it would have printed the same dependency a second time); it stays only for version overrides and resolutions, which the other code does not read, under the name "Override Added". I also fixed one grammar slip in the kept message ("1 dependency that were not checked") and added two tests: one that an override is named once and not forgiven as old, one that a dependency is never reported twice.
4. **Scripts:** the testing-plan version of the runner and speed test is a superset of the patch session's edits (it has the unknown-group and no-stage exits, and reads the scale sizes from the budgets file), so it replaces them. `release-check.mjs` still has the import-cycle step (D-o).
5. **`claims.json`:** merged by claim id. F03-02 got one combined `fix` block. F07-06 got the second session's text, dated 2026-11-12, with its two evidence quotes changed to match the kept code. F05-09 is the patch session's. The checks page was regenerated, not merged as text.
6. **`packages/mcp-server/server.json`:** the 11-11 handoff says it was deleted (D-h) and the checked-in docs say so, but the file was still in `packages.zip`. I deleted it. Nothing references it.
7. **Dropped from the tree:** `index_headline.test.ts`, `scripts/benchmark-cli-help.mjs`, `purix-mcp-smoke-test.mjs`, the earlier F03-02 draft.
8. **Duplicate sweep (second pass, 11-12).** I searched the merged tree for the same work done twice. Three real duplicates were found and removed: (a) the E3c behaviour was tested twice, five tests in `oscillation_guard.test.ts` (patch session) and six in `heal.test.ts`, `escalate_infrastructure.test.ts` and `resolve_verification.test.ts` (other session), so the five were deleted and the F07-06 evidence quote now points at the kept test; (b) a git, URL or path dependency was reported twice, once as "Dependency Source" and once inside the "not checked" note, so the note now leaves out what `manifest_delta.ts` already judged; (c) the two original handoffs now carry an "already merged, do not apply" banner so nobody applies the patch a second time. Accepted on purpose: package.json is parsed in two places (`gates/manifest_delta.ts` reads sections for blocking rules and overrides, `security/dep_delta.ts` reads exact versions for the lookup), and the two modules answer different questions. Pre-existing and left alone: four pairs of identical files under `docs/compliance/` (a copy at the top level and one in `iso-42001/` or `eu-ai-act/`), which were already in `packages.zip` and belong to the compliance sweep in 6.2. No file arrived twice from different uploads, no test title repeats across the touched folders, and no other source function was duplicated.
